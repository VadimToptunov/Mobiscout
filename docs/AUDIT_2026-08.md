# Audit — Mobiscout 0.10.0 (2026-08-22)

A second evidence-based pass over the whole project, complementing the July
engineering review in [CODE_REVIEW.md](CODE_REVIEW.md). That one asked *is the
code internally sound?*; this one asks **does the project do what it says it
does?** — claims in the README / docs checked against the code that would have to
back them, plus the generated output checked by running the real pipeline.

Every finding below is either read first-hand at `file:line` or reproduced live,
with the repro command included. Where a finding is an observation rather than a
defect, it is labelled as such.

## 1. P0 — `python_pytest` emits positive tests that use negative-case data

**The defect.** [`templates/python_pytest/test_file.py.j2:88`](../framework/codegen/templates/python_pytest/test_file.py.j2)
collects every `type` step across **all** cases into one flat list, then emits one
`TEST_DATA` entry per step keyed by field name
([`_data_key`](../framework/codegen/emitters/python_pytest.py) — the snake_cased
field label). Nothing deduplicates. Once a model carries both a positive and a
negative case touching the same field, the keys collide and Python silently keeps
the **last** binding.

**Reproduced live** (`python examples/generate.py` output, Login → Catalog → Cart):

```python
TEST_DATA = {
    "email": "test@example.com",
    "password": "Password123!",
    "search_products": "test",
    "email": "test@example.com",       # duplicate
    "password": "Password123!",
    "search_products": "test",
    "email": "not-an-email",           # negative case — overwrites both above
    "password": "1",
}
```

What the interpreter actually sees:

```
{'email': 'not-an-email', 'password': '1', 'search_products': 'test'}
```

**Consequence.** `test_journey_from_sign_in_to_add_to_cart` and
`test_journey_from_sign_in_to_cart` type invalid credentials and then assert they
reached the Catalog screen. They are guaranteed red against a real app. This is
the flagship target *and* the test shown in the README as the product's showcase,
so it directly contradicts the core promise ("our generated tests actually pass in
CI").

**Scope.** `python_pytest` only. `java_testng`, `js_webdriverio` and both BDD
targets inline per-case values and are correct — verified in the same generated
kit.

**Why the goldens miss it.** `tests/codegen/golden/python_pytest/test_login_flow.py:70`
comes from a fixture with a single input field and a single case, so no collision
can occur. The golden is byte-correct and still blind to this.

**Fix direction (owner's call).** Keys must be unique per *(case, field)*, not per
field. Cleanest surgical shape: build the mapping in the emitter (Python), not in
the template — dedupe on `(key, value)` and disambiguate a colliding key with a
case-derived suffix, leaving the template a dumb renderer. Regression test: a model
with a positive **and** a negative case typing into the same field; assert
`ast.literal_eval` of the emitted `TEST_DATA` has as many entries as distinct
values.

Repro:

```bash
python examples/generate.py && sed -n '/^TEST_DATA = {/,/^}/p' examples/shop_demo/flat/python_pytest/test_crawl_flow.py
```

## 2. Claims the code does not support

### 2.1 The Rust core is not wired to anything

`mobiscout_core` is **not imported by a single Python file** in the repository
(`grep -r mobiscout_core --include='*.py'` → no hits outside `rust_core/` itself and
three docs). 1830 lines of Rust that `ci.yml` compiles on three OSes and uploads as
wheels, reachable from no code path.

Against that, the documentation states as fact:

| Claim | Location |
| --- | --- |
| 🦀 in the project title, Rust badge | `README.md:1`, `README.md:7` |
| "The Rust core is exposed to Python via PyO3" | `README.md:565` |
| Architecture diagram with a `PyO3` arrow into the core | `README.md:552` |
| "Rust Core (90%) — All performance-critical operations" | `docs/ARCHITECTURE.md:109` |
| "18x faster than Python", "250 MB/s" | `docs/ARCHITECTURE.md:213`, `:215` |
| "2M events/second" | `docs/ARCHITECTURE.md:221` |
| "1.5 GB/s" | `docs/ARCHITECTURE.md:235` |
| Full benchmark table (18x / 20x / 16x / 11x) | `docs/ARCHITECTURE.md:555` |

No benchmark harness exists to have produced any of those numbers —
`rust_core/Cargo.toml:57` reads *"Benchmarks (commented out until implemented)"*
and both `[[bench]]` targets are commented out. `docs/RUST_CORE.md` repeats the
same figures.

This is the project's single largest exposure. For a codebase whose differentiator
is honesty about what it does and does not do, one reader running that grep
discredits the rest of the documentation. Two coherent resolutions, no third:

- **Wire it** — put the core on a real path (AST/SAST analysis is the obvious
  candidate), add the benchmark harness, and replace the table with measured
  numbers from it; or
- **Retire it** — move `rust_core/` out of the repo, drop the `build-rust` CI job,
  and delete every Rust claim from `README.md`, `docs/ARCHITECTURE.md`,
  `docs/TECHNICAL_DESIGN.md` and `docs/RUST_CORE.md`.

Leaving it as-is is worse than either.

### 2.2 `CHANGELOG.md` describes a timeline that never happened

Entries run "Phase 1 — 2024-09" through "Phase 6 — 2025-01-29". The repository's
**first commit is 2025-12-19** (`git log --reverse | head`). Every date predates the
project's existence. There is no entry for 0.9.0, 0.9.1 or 0.10.0, and the file's
subtitle still reads "Mobile Mobiscout & Test Framework" — a rename artifact.

The git history is detailed and PR-linked; regenerating the changelog from it is
mechanical and would make the file true.

### 2.3 `examples/shop_demo/` is stale

`python examples/generate.py` produces materially different output from what is
committed: condition-based waits, the `settle()` beat, readable scenario names, and
negative cases are all in today's generator and absent from the committed files,
which are still signed *"auto-generated by Mobile Test Recorder"* (the pre-rename
name). `README.md:28` presents these files as "what comes out".

Regenerating fixes this — but see §1 first: regenerating today bakes the
duplicate-key bug into the showcase. **Fix §1, then regenerate.**

## 3. Commands that report success without doing the work

Three CLI/API surfaces print or return success for work they never performed. Each
is a small fix, but each is exactly the "dead-on-arrival command" class that
[CODE_REVIEW.md §6](CODE_REVIEW.md) already flagged as this codebase's recurring
failure mode.

**`mobiscout load profile <test_path>`** —
[`cli/load_commands.py:219`](../framework/cli/load_commands.py). Echoes
`Profiling: {test_path}`, then profiles a local `test_function()` whose entire body
is `time.sleep(0.1)`. The user's tests are never executed; the reported duration and
memory figures describe the sleep.

**`mobiscout devices pool create`** —
[`cli/device_commands.py:229`](../framework/cli/device_commands.py). Loops over the
requested device IDs, prints `Added device: …` for each, increments a counter, and
reports `✅ Created pool 'X' with N devices` — but never calls
`DevicePool.add_device`, which has **zero callers repository-wide**
([`devices/device_pool.py:47`](../framework/devices/device_pool.py)). Every pool is
empty; any later allocation from it returns nothing.

**`POST /api/selectors/{id}/approve`** —
[`dashboard/server.py:106`](../framework/dashboard/server.py). Updates the DB row
and returns `{"status": "approved"}`; the source file is never written and nothing
is committed. The inline comment is honest ("In real implementation, this would
trigger actual file update and git commit") but the HTTP response is not.

For each: implement, or delete the command, or make the output state plainly that
it is a stub — the same treatment the fuzzer already gets
(`fuzzing/fuzzer.py:406` returns `simulated=True` rather than inventing a result).
That pattern is the right precedent; these three predate it.

## 4. `--style pom` is far thinner than the README implies

From an identical crawl, verified by generating both from the same model:

| Style | Tests emitted | Form filling | Multi-step journeys | Negative cases |
| --- | --- | --- | --- | --- |
| flat (`python_pytest`) | 8 | yes | yes | yes |
| `--style pom` | **1** | no | no | no |

The single POM test is a two-screen navigation assertion. `README.md` presents POM
as a structural variant of the same output ("Framework structure, not loose
files"), which reads as parity. Either bring the POM path up to the flat path's
coverage, or say in the README what POM currently emits.

Not a defect — a capability gap described inaccurately.

## 5. Test-surface gaps

- **The JetBrains plugin has no tests at all.** 3,616 lines of Kotlin across 25
  files; `jetbrains-plugin/src/` contains only `main/`. CI runs `buildPlugin` and
  `verifyPlugin` — compile and manifest checks, not behaviour. Since 0.10.0 made the
  plugin the single user-facing path, the untested layer is now the product surface.
  `JsonRpcClient`, `EngineProvider` and `MTRDaemonService` are the highest-value
  first targets (protocol framing, engine discovery/download, process lifecycle).
- **Cyclomatic complexity is not enforced.** `ci.yml:46` runs the complexity pass
  with `--exit-zero`, so it can only ever warn. At threshold 12 there are **38**
  C901 functions, worst `cli/business_logic_commands.py:43` (23),
  `cli/ci_commands.py:151` (22), `cli/healing_commands.py:138` and
  `cli/generate_service.py:169` (21 each). Either ratchet a real threshold or drop
  the pass.
- **`interrogate` has 0.8% of headroom** (90.8% vs floor 90). The next few
  undocumented functions will red the lint job for an unrelated reason.
- **`features/` and `test_scenarios.yaml` are not git-ignored.** `CLAUDE.md` warns
  "never commit them"; both are sitting untracked in the working tree right now.
  A `.gitignore` entry converts a standing manual rule into an enforced one.

## 6. Observation — where the mass sits

Not a defect, but worth a deliberate decision:

| Package | LOC | On the plugin's path? |
| --- | --- | --- |
| `cli/` | 13,475 | partly (`daemon_commands` only) |
| `security/` | 8,314 | no |
| `crawler/` | 5,565 | **yes — the core** |
| `codegen/` | 3,071 | **yes — the core** |

There are 38 CLI command groups. The plugin — "the one path" as of 0.10.0 — calls
20 RPC methods, which together reach roughly six of them. The security package
alone is 50% larger than the crawler that constitutes the product's actual value,
and its code is good (real analysis, honest about its floor at
`security/scanner.py:299`), which makes it harder, not easier, to leave aside.

The question this raises is not "is this code bad" but "what is 1.0 for". Depth on
crawl → kit is what `ROADMAP.md` commits to; the breadth is not on that path.
